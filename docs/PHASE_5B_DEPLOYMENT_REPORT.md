## Arsitektur dan anggaran

Tiga proses aplikasi berjalan terpisah. Web menyajikan Next.js, atlas, aset terbundel, API warga, pemilu dan admin. Colyseus memerlukan satu replika terus aktif dengan WebSocket, tanpa scale-to-zero. Worker backup privat tidak memerlukan domain. Database PostgreSQL memakai volume persisten dan jaringan privat Railway. Prosedur staging tidak menggunakan SQLite sebagai fallback. Layanan lokal Phase 1–5 tetap dapat berjalan di profil development.

Railway Hobby memiliki minimum US$5/bulan, diperhitungkan terhadap pemakaian. Contoh anggaran ilustratif untuk gabungan layanan: RAM rata-rata 1,5 GB × $10, CPU rata-rata 0,2 vCPU × $20, volume 5 GB × $0,15, serta egress 10 GB × $0,05 menghasilkan sekitar **US$20,25/bulan** sebelum AWS, pajak dan variasi penggunaan. Ukuran aktual baru dapat diukur setelah deployment. S3 mengenakan biaya storage, permintaan dan transfer menurut region; anggaran contoh Railway belum memasukkan komponen itu. Alternatif yang dibandingkan saat pemilihan adalah Render dengan layanan selalu aktif dan managed PostgreSQL. [Tarif Railway](https://docs.railway.com/pricing) · [Tarif AWS S3](https://aws.amazon.com/s3/pricing/) · [Tarif Render](https://render.com/pricing)

Antarlayanan Railway menggunakan DNS internal dan jaringan WireGuard. Driver meminta TLS dengan pemeriksaan sertifikat untuk koneksi di luar loopback/domain privat Railway. Gunakan PG_CA_PEM untuk CA tambahan bila diperlukan. [Jaringan privat Railway](https://docs.railway.com/networking/private-networking)

## Prosedur provisioning dan cutover

1. Hubungkan Railway melalui integrasi resmi, pilih workspace dan environment staging. Sepakati biaya serta batas anggaran. Pisahkan project/environment development, staging dan production. Persetujuan memilih Railway untuk perencanaan berbeda dari persetujuan menjalankan resource berbayar atau membuka domain.
2. Setelah disetujui, siapkan PostgreSQL 15+ persisten di staging. Buat database staging kosong, database drill terpisah dengan **nama database berbeda**, serta role LOGIN runtime biasa (contoh nation_app), tanpa SUPERUSER, BYPASSRLS, CREATEDB, CREATEROLE, REPLICATION atau membership pada role pemilik. Restriksi akses jaringan ke lingkungan operator atau private networking. Owner digunakan hanya untuk migrasi dan drill. Simpan URL owner serta password melalui secret manager. Jangan menyalin URL owner ke DATABASE_URL layanan aplikasi.
3. Siapkan bucket khusus AWS S3 dan identitas IAM sesuai BACKUP_AND_RECOVERY.md. Aktifkan Block Public Access, BucketOwnerEnforced dan lifecycle satu hari pada nation-backups/. Kunci 32 byte Base64 berada di secret manager terpisah, termasuk salinan pemulihan. Identitas worker membutuhkan metadata privasi bucket, GetBucketPolicy/Status, GetBucketVersioning, GetLifecycleConfiguration, PutObject dan GetObject terbatas pada prefix. Web dan multiplayer tidak memerlukan AWS credentials atau BACKUP_KEY.
4. Tentukan file SQLite otoritatif dengan operator. Bekukan penulisan lokal sebelum cutover. Dari terminal operator tepercaya yang memiliki akses kedua target, atur MIGRATION_SOURCE, MIGRATION_DATABASE_URL, MIGRATION_TARGET_DATABASE, RUNTIME_DB_ROLE, BACKUP_DIR, BACKUP_KEY, AWS_REGION dan BACKUP_S3_BUCKET. Jalankan `node scripts/staging-migrate.mjs --confirm-new-schema`. Skrip membuat backup WAL terenkripsi, memverifikasi upload lewat baca balik, lalu memulihkan salinan itu ke file sementara. Impor menolak schema nation_import yang sudah ada. Jumlah serta signature kanonik **setiap tabel** dibandingkan sebelum commit. Pertahankan sumber lokal read-only setelah cutover.
5. Atur tiga service dari revisi source yang telah diuji. Root build adalah root repo. Pada masing-masing service pilih config-as-code deploy/railway/web.toml, multiplayer.toml atau backup.toml. Ketiganya memakai deploy/railway/Dockerfile. Template variabel ada di deploy/railway/staging.env.example. Satu proses per service, shutdown via SIGTERM dan restart ON_FAILURE. Nonaktifkan serverless sleeping untuk multiplayer dan worker. Dockerfile disiapkan; build image Railway/Docker masih perlu dijalankan pada target. [Config as code Railway](https://docs.railway.com/reference/config-as-code)
6. Gunakan NATION_ENV=staging, NATION_DB=postgres dan DATABASE_URL dengan role runtime pada ketiga service. Web/Colyseus memerlukan WEB_ORIGIN (origin HTTPS lengkap), CLOSED_BETA=true, BETA_USERNAMES serta BETA_INVITE_KEY acak minimal 32 karakter. Web memerlukan ADMIN_KEY berbeda dan MULTIPLAYER_PUBLIC_URL dengan skema wss. Port layanan menggunakan PORT dari Railway. Asset prosedural, JS dan CSS ikut di dalam image. Backup worker sendiri menerima AWS_REGION, BACKUP_S3_BUCKET, kredensial IAM, BACKUP_KEY dan BACKUP_INTERVAL_HOURS (contoh 12).
7. Setelah izin membuka akses publik diberikan, gunakan domain platform untuk web dan Colyseus, masukkan origin aktual ke konfigurasi dan redeploy. Untuk domain sendiri, gunakan custom domain Railway, pasang DNS yang ditampilkan provider, tunggu sertifikat valid, lalu sesuaikan WEB_ORIGIN dan MULTIPLAYER_PUBLIC_URL. Pastikan /api/health dan /health HTTP 200, cookie sesi bertanda Secure dan HttpOnly, upgrade WSS berhasil dari origin beta, dan origin lain ditolak. Jangan menyimpulkan online dari log startup saja.
8. Untuk pendaftaran, tetapkan username samaran di allowlist. Dari **terminal operator privat**, dengan secret staging terpasang, jalankan `node scripts/issue-beta-invite.mjs USERNAME`. Serahkan kode individual melalui saluran privat. Satu kode terikat pada satu username; username yang telah diambil tidak bisa diregistrasi ulang. Login akun lama juga memerlukan allowlist; pencabutan nama membatalkan akses sesi warga saat pemeriksaan berikut. Jangan menampilkan master key atau mencatat kode dalam log CI.
9. Setelah dapat mengakses URL aktual, ulangi dua login beta pada dua perangkat dan jaringan berbeda, cek gerakan, chat dekat/jauh pada frame WebSocket, perubahan area, reconnect, pemerintahan, admin, dan akses dari luar allowlist. Simpan hasil URL, tanggal, perangkat, jaringan dan commit yang diuji. Gate internet masih terbuka sampai bukti itu tersedia.

## Backup PostgreSQL, monitoring dan rollback

Worker memakai satu snapshot transaksi REPEATABLE READ READ ONLY untuk tabel game dan akun, membuang token/tiket serta bukti moderasi dekat expiry, mengompresi JSON dan mengenkripsi AES-256-GCM sebelum pengiriman. SHA-256 ciphertext diperiksa lewat GET S3. Job manual dari /pemulihan masuk ke backup_runs. Worker memakai advisory lock, menyimpan status requested/running/verified/failed dan menulis log ID, ukuran serta hasil tanpa isi database. Logis ini adalah backup aplikasi; role server PostgreSQL, secret, konfigurasi provider, token dan tiket perlu dipulihkan secara terpisah. Kebijakan remote satu hari dirancang untuk salinan operasional dengan bukti moderasi. Uji RPO, lifecycle provider dan jadwal sebelum mengandalkannya.

Untuk drill, atur DATABASE_URL ke staging sumber, RESTORE_DATABASE_URL ke database drill kosong dengan role pemilik, RESTORE_TARGET_DATABASE ke nama drill, serta RUNTIME_DB_ROLE dan secret S3/key. Jalankan `node scripts/staging-backup.mjs restore-drill ID --confirm-new-schema`. Alur memeriksa metadata, checksum, tag GCM, FK, jumlah baris, dan signature; status restore hanya dicatat setelah transaksi import tujuan berhasil. Bandingkan riwayat dunia dan hasil pemilu, lalu lakukan login ulang pada environment drill. Isi backup tidak tersedia untuk diunduh dari browser.

Gunakan log Railway dan health check untuk memantau restart, matchmaking, kegagalan DB, usia job terakhir dan checksum. Tetapkan alert eksternal untuk backup gagal atau terlambat; konfigurasi alert dan notifikasi operator belum diuji di akun hosting. Untuk rollback aplikasi gunakan deployment PostgreSQL sebelumnya yang kompatibel. Jika memerlukan rollback data, hentikan web, multiplayer dan worker, simpan snapshot pengaman, pulihkan ke database baru lalu alihkan seluruh layanan sekaligus. Menyalakan kembali SQLite yang sudah tertinggal memerlukan rekonsiliasi perubahan staging terlebih dahulu.

## Catatan teknis

Schema PostgreSQL menggunakan PK/FK asli, constraint unik pada participation dan penguncian transaksi lintas proses. Untuk mempertahankan reducer sinkron yang dipakai sejak Phase 1, setiap proses aplikasi memakai satu koneksi PostgreSQL pada worker thread. Ini memblokir eksekutor domain selama round trip. Gunakan satu region, satu replika Colyseus, closed beta kecil, dan ukur latensi serta event-loop lag sebelum menaikkan kuota. Tidak ada angka kapasitas online yang telah diverifikasi. Restore dan backup logis saat ini menggunakan memori sesuai ukuran dataset.

Pengujian reproducible: `npm ci`, `npm run typecheck`, `npm run build`, `npm test`, dan `node tests/postgres-runtime.mjs --mobile`. Tes terakhir memerlukan Edge dan izin membuka port loopback. Tes menjalankan binary PostgreSQL sungguhan terhadap data sintetis, memeriksa undangan, pergerakan sentuh, chat, perjalanan ke Sagara, reconnect, voting, dan memulihkan arsip ke database kedua. Sertifikat sementara diterima hanya oleh browser pengujian lokal. Tidak ada sertifikat test atau credential database disertakan dalam source.

## Tindakan pemilik yang masih diperlukan

Hubungkan workspace Railway dan tentukan database sumber SQLite. Konfigurasikan credential server dan bucket lewat Railway Variables/AWS IAM, tanpa mengirim secret melalui chat. Konfirmasi batas pengeluaran, target environment dan izin publikasi HTTPS/WSS. Setelah itu baru dapat dilakukan migrasi ke instance staging, upload/restore nyata, dan uji lintas jaringan.
